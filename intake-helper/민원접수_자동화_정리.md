# 민원접수 자동화 프로그램 정리

작성일: 2026-10-08
대상: 시험검사의뢰서(사진·PDF·엑셀)를 읽어 연구관리시스템(KAFRI) 민원접수관리 → 민원접수 등록 화면 값으로 바꾸고, 사람이 확인한 뒤 접수하는 프로그램

이 문서는 지금까지 나눈 내용, 결정 사항, 이번에 만든 테스트 버전의 사용법, 남은 일을 한곳에 모은 것입니다.

---

## 1. 한눈에 보기

| 항목 | 상태 |
|---|---|
| 의뢰서 사진 → 엑셀 추출 | 가능. 판독이 불확실한 칸은 노란색으로 표시하고 사람이 확인 |
| 엑셀 → 민원접수 등록 값 변환·검증 | 이번 테스트 버전에 구현 |
| 과거 접수에서 업체 정보 가져오기 | 구현(읽기 전용). 서버 응답 컬럼명은 실제 연결 후 확인 필요 |
| 코드 매핑(의뢰목적·보관방법·통보방법) | 기초코드 조회로 구현. 식품유형·검사항목 코드는 미구현 |
| 서버에 실제 저장 | **미구현.** 저장 요청 규격을 아직 캡처하지 못함 |
| 시료번호 일괄 발생 | 별도 화면의 기능. 이번 범위 밖(후속) |

핵심 결론: 접속 방식은 이미 확보되어 있습니다(사번 로그인). 부족한 것은 키가 아니라 **민원접수 등록 화면의 저장 요청 규격**입니다.

## 2. 받은 자료와 확인 결과

1. **시험검사의뢰서 사진**(2026-10-02자, 광동헬스바이오(주) 2공장, 올리브유 캡슐, 벤조피렌 1항목). 90도 회전된 사진이고 접수번호는 빨간 손글씨입니다.
2. **의뢰서 엑셀**(`의뢰서목록` 시트, 1행=의뢰서 1건, 28열). 노란 칸(접수번호, 성적서 전달방법, 시료구분, 비고)은 판독이 불확실한 항목입니다.
3. **민원접수 등록 화면 캡처 2장**: 빈 화면, 그리고 저장 후 예시(아워홈, 접수번호 2610-0685).
4. **`kafri-core.js`와 KAFRI 시험본 압축 파일**: 연구관리시스템(MiPlatform) 접속 코드.
   - API 키 파일이 아닙니다. 로그인은 **사번만** 보내고 비밀번호가 없습니다(세션 쿠키 사용).
   - 구현된 것: 로그인, 조회(접수현황 `CHEC0010`, 민원접수 현황 `ACCE0020`, 시료 상세 `CHEC0020`), 기초코드 전수 조회(`BASE0080`, 82그룹·853코드), 검사결과 저장, 첨부 저장.
   - 없는 것: 민원접수 **등록** 저장, 업체·식품유형·검사항목 검색.
   - 압축 파일 안에 키·인증서·`.env` 파일은 없습니다. `KOSHA_MSDS_API_KEY`(안전보건공단 MSDS)만 `.env`에서 읽도록 되어 있고 KAFRI와 무관합니다.

### 예시 화면(저장 후)에서 알게 된 사실
- 접수번호(2610-0685)와 시료번호(2026-11-017501)는 서버가 부여합니다. 의뢰서의 손글씨 번호는 입력하지 않습니다.
- 의뢰업체를 고르면 대표자, 주소, 계산서 업체, 사업자번호, DM 주소가 자동으로 채워집니다.
- **제조일자·제조번호·유통기한은 노란 칸인데도 비어 있는 채로 저장**되었습니다. 의뢰서에 '-'로 적힌 제조일자는 공란으로 두면 될 가능성이 높습니다(캡처로 확정 필요).
- 시료량은 숫자와 단위(`100.00 g`)입니다.
- 검사금액, DC율, 합계금액(143,000 / 10% / 128,700), 내부기한·처리기한은 검사항목을 고르면 자동 계산되는 값으로 보입니다.
- 한글·영문 부수, 검체수, 통보방법(우편)은 별도 필드입니다.
- 화면은 윈도우 데스크톱 클라이언트(KAFRI [민원접수등록])입니다.

| 검사항목 그리드 | 시험항목, 기준 | 항목코드·금액 조회 필요(미구현) |
| DM 업체·주소 | 성적서 수령주소 | 용도 확인 필요 |

## 4. 결정 사항

| 주제 | 결정 |
|---|---|
| 접수 단위 | **시료 1건 = 접수 1건.** 한 의뢰서에 시료가 여러 개면 의뢰서 공통 정보를 반복해 여러 건으로 나눔. 검사항목은 한 접수 안에서 여러 줄 |
| 복잡한 의뢰서(별첨, 여러 쪽, 시료 여러 개) | 파일들을 하나의 **의뢰 묶음**으로 읽고, 접수 양식에 맞는 엑셀로 변환한 뒤 접수 |
| 업체 정보 | 과거 접수 내역에서 미리 가져와도 됨. **의뢰업체와 계산서 업체가 달라도** 사용 가능. 의뢰서와 다른 값은 표시하고 사용자가 선택 |
| 시료번호 | 접수와 별개로 다른 화면에서 여러 건을 한꺼번에 발생시킬 수도 있음. 후속 기능으로 두고, 접수 결과에 접수번호 목록을 남김 |
| 입력 방식 | 의뢰서 1개씩 접수, 폴더를 골라 여러 건을 한꺼번에 접수. 둘 다 같은 처리 과정을 공유 |
| 테스트 버전 범위 | 엑셀 불러오기 + Claude API 추출 둘 다 지원, 서버 저장은 **드라이런**(전송될 값 미리보기까지), 등록 모듈은 자리만 마련 |
| 구현 방식 | 화면 클릭 자동화가 아니라 **원본 프로그램이 서버와 주고받는 요청을 그대로 재현** |

### 방식 비교
| 방식 | 장점 | 단점 |
|---|---|---|
| 서버 요청 재현(채택) | 빠르고 안정적, 화면 해상도·창 위치와 무관, 저장 후 재조회 대조 가능 | 저장 요청 규격을 캡처해야 함. 요청 형식이 까다로움 |
| 화면 자동화(RPA) | 서버 규격을 몰라도 가능 | 이 클라이언트는 커스텀 컨트롤이라 요소 인식이 어렵고 느리며 깨지기 쉬움 |
| 개발사·관리자에 요청 | 가장 정식 | 일정과 협의 필요 |

## 5. 전체 흐름과 엑셀 양식

의뢰서 파일 → ① 추출(JSON/엑셀) → ② 사람 확인(노란 칸) → ③ 코드 매핑·업체정보 조회 → ④ 등록 저장 → ⑤ 재조회 대조 → 결과 기록

### 엑셀 3시트 양식
| 시트 | 한 행의 의미 | 내용 |
|---|---|---|
| 접수 | 접수 1건(시료 1건) | 접수ID, 원본파일, 업체·의뢰인, 계산서, 성적서·의뢰목적, 시료, 확인필요 항목(노란 칸) |
| 시험항목 | 접수 1건의 항목 1줄 | 접수ID, 시험항목, 기준, 비고 |
| 검증 | 오류·확인 사항 1건 | 접수ID, 수준, 항목, 내용 |

접수ID로 접수와 시험항목을 연결합니다. 예전 양식(`의뢰서목록`, 1행=의뢰서 1건)도 불러와 새 양식으로 변환합니다.

### 복잡한 의뢰서 처리 규칙
- 본지와 별첨은 하나의 묶음으로 읽고, 각 항목에 근거 파일·쪽을 기록합니다.
- 본지에 "별첨 참조"라고만 있으면 별첨에서 시료·항목을 가져오고, 별첨이 없으면 접수를 만들지 않고 "별첨 누락"으로 표시합니다.
- 시료×항목 표는 시료별 항목 행으로 풀어 씁니다.
- 판독이 모호한 칸은 추측으로 채우지 않고 노란색과 사유로 표시합니다. 변환이 어려운 의뢰서는 "수기 처리 필요"로 분류합니다.

## 6. 안전장치

- 기본은 드라이런이고, 화면 위에 "서버에 저장하지 않음"이 항상 표시됩니다.
- 읽자마자 저장하지 않습니다. 추출 → 사람 확인 → 확정 → 등록의 단계를 둡니다. 오류가 있으면 확정할 수 없습니다.
- 등록 전에 최근 30일 같은 업체·시료명(같은 제조번호) 접수를 조회해 중복을 막습니다.
- 업체·코드가 맞지 않으면 임의로 만들지 않고 중단해 사유를 보여 줍니다.
- 저장 후 재조회로 모든 값을 대조합니다(실제 등록 모듈 연결 시).
- **계산서 업체 확인**: 의뢰서의 사업자번호와 가져온 계산서 업체의 사업자번호가 다르면 자동으로 넘어가지 않고 확인을 요청합니다(계산서 오류는 청구 문제로 이어집니다).
- 처리한 파일은 삭제하지 않고 완료 표시만 합니다.

## 7. 이번에 만든 테스트 버전 (접수 도우미 0.1.0)

### 구성
- 사용자 PC에서 실행하는 로컬 웹 프로그램입니다. `시작.bat`을 실행하면 브라우저가 열립니다(127.0.0.1에서만 접속 가능).
- 서버 코드는 외부 라이브러리 없이 Node.js로 작성했고, 엑셀 처리에만 `exceljs`를 씁니다(`node_modules`에 포함).
- 접속 코드는 기존 `kafri-core.js`를 그대로 재사용했습니다.

### 실행 방법
1. 압축을 풀고, 사용하시는 `node.exe`를 폴더에 복사합니다(또는 PC에 Node.js 설치).
2. `시작.bat`을 더블클릭합니다. 검은 창은 닫지 마세요.
3. 연구관리시스템 없이 화면만 보려면 `시작_데모.bat`(꾸민 데이터)을 사용합니다.
4. 사진·PDF를 AI로 읽으려면 `.env.example`을 `.env`로 복사하고 `ANTHROPIC_API_KEY=`에 키를 넣습니다. 키가 없으면 엑셀 불러오기만 가능합니다.

### 화면 단계
1. **불러오기**: 의뢰서 사진·PDF(여러 파일 선택 시 "한 건의 의뢰로 읽기"/"파일마다 따로"), 폴더 일괄(하위 폴더 = 한 의뢰), 엑셀.
2. **검토**: 접수 현황 띠(건마다 한 칸), 건 목록, 원본과 입력값 나란히 보기, 노란 칸(확인 필요) 처리, 과거 접수에서 업체 정보 가져오기, 중복 접수 확인, 건 확정.
3. **등록(드라이런)**: 확정한 건의 업체코드·코드 매칭·중복 점검, 서버로 보낼 값 미리보기. "서버에 접수" 버튼은 저장 규격 확보 전까지 꺼져 있습니다.
- 어느 단계에서든 "엑셀로 저장"(3시트)과 "기초코드 보기"를 쓸 수 있습니다.

### 이번에 검증한 것 (개발 환경, 연구관리시스템 접속 없이)
- 예전 양식 엑셀 불러오기와 새 양식 저장·재불러오기 왕복(노란 칸 보존).
- 모의 AI 응답으로 사진 2장을 한 묶음으로 읽어 접수 2건(별첨에서 시험항목 누락 건은 오류로 표시)으로 만드는 경로.
- 검토 → 확정 → 드라이런 → 엑셀 저장의 화면 흐름, 모바일 폭 배치, 접속 차단 시 오류 문구.
- 보관방법 "상온"이 코드표의 "실온"과 매칭되지 않던 문제를 찾아 보정.

### 아직 검증하지 못한 것 (실제 환경에서 확인해야 함)
- **실제 연구관리시스템 접속**: 사번 로그인, 업체 조회, 기초코드 조회. 개발 환경에서는 사내 서버에 접속할 수 없습니다.
- **과거 접수 응답의 컬럼 이름**: 업체코드·대표자·주소·계산서 업체 컬럼을 이름 규칙으로 추정합니다. 화면의 "서버에서 받은 컬럼 보기"에서 실제 컬럼을 확인하세요. 인식하지 못하는 항목이 있으면 알려주시면 규칙을 고칩니다.
- **실제 Claude API 호출**: 모의 응답으로 경로만 검증했습니다. 판독 정확도는 실제 의뢰서로 확인이 필요합니다.
- **기초코드 그룹 이름**: 의뢰목적·보관방법·통보방법 그룹을 이름으로 찾습니다. "코드그룹 없음"이 나오면 "기초코드 보기"로 실제 그룹 이름을 확인하세요.

### 권장 테스트 순서
1. `시작_데모.bat`으로 화면 흐름을 한 번 익힙니다(사번 아무 숫자 입력).
2. `시작.bat`으로 실제 연결: 사번 연결 → 예전 엑셀 불러오기 → "과거 접수에서 업체 정보 가져오기"로 컬럼 인식 확인 → "기초코드 보기".
3. 의뢰서 사진 몇 장(단순 1건, 별첨 포함, 시료 여러 개)을 AI로 읽어 정확도 확인.
4. 확정 후 드라이런으로 "점검 통과" 비율과 미해결 칸을 확인.

## 9. 보안·운영 주의

- **의뢰서 이미지는 Claude API(외부 서비스)로 전송됩니다.** 의뢰서에는 업체명, 연락처, 사업자번호가 들어 있습니다. 사용 전에 기관의 정보보안·개인정보 정책을 확인하세요. 엑셀 불러오기만 쓰면 외부로 전송되지 않습니다.
- API 키는 `.env`에만 두고 다른 사람과 공유하지 마세요. 이 프로그램은 키를 화면·로그·엑셀에 남기지 않습니다.
- 접수자는 연결한 **사번으로 기록**됩니다. 실제 등록 기능을 연결하기 전에 연구관리시스템 담당자와 협의하세요.
- 사번은 메모리에만 두고 창을 닫으면 사라집니다. 기존 접속 코드는 요청에 고정 IP 값(127.0.0.100)을 보내므로, 운영 전 관리자와 확인하는 것이 좋습니다.
- 프로그램은 127.0.0.1에서만 열리며, 다른 사이트에서 오는 요청은 거부합니다.
- 브라우저를 닫으면 불러온 내용이 사라집니다. 작업 도중에는 "엑셀로 저장"을 사용하세요.

## 12. 읽기 방식 개편: API 키 없이 쓰는 A+B 혼합 (0.2.0, 2026-10-10)

API 키 없이도 변환할 수 있도록 두 방식을 섞어 쓰는 구성으로 바꿨습니다.

| 방식 | 대상 | API 키 | 동작 |
|---|---|---|---|
| **B. 고정 양식 규칙 변환** | 항상 같은 양식으로 오는 docx · hwpx · 글자가 살아 있는 PDF | 불필요 | 이 PC에서 문서의 표·글자를 펴서 `rules/*.json` 의 라벨 사전("업체명", "핸드폰" …)으로 값을 찾아 접수로 변환 |
| **A. Claude 앱 변환** | 사진, 스캔본, 손글씨, 양식이 제각각인 의뢰서 | 불필요(Claude 구독) | 화면의 "변환 방법 보기"에서 빈 양식 엑셀을 받고 요청문을 복사 → Claude 앱에 사진과 함께 올려 엑셀을 받음 → "엑셀 선택"으로 불러옴 |
| (기존) AI 읽기 | 사진·PDF | 필요 | `.env` 에 키가 있을 때만. 키가 있으면 PDF는 규칙 → 안 되면 AI 순서 |

### B 방식 동작과 한계
- 읽는 대상: docx, hwpx(한글 저장 형식), 글자 층이 있는 PDF. `.hwp`, `.doc` 는 hwpx, docx 로 다시 저장해야 합니다.
- 좌우로 나란한 구역(의뢰인 | 계산서)과 같은 라벨(업체명, 주소, 이메일, 대표자)을 열 위치로 구분합니다. 구역을 알아보지 못해 나온 순서로만 판단한 값은 노란 칸(확인 필요)으로 표시합니다.
- 체크박스(■ ☑ ☒ / □ ☐)는 선택된 칸의 글자만 값으로 씁니다. 시료표는 한 행이 접수 1건이고, 한 칸의 여러 줄은 시험항목 여러 개가 됩니다.
- 양식에 맞지 않으면 추측하지 않고 "고정 양식과 맞지 않습니다"로 멈춥니다. 스캔 PDF는 "글자 정보가 없습니다"로 멈추고 A 방식을 안내합니다.
- **기본 규칙(`rules/기본양식.json`)은 알려진 양식 구성을 바탕으로 한 추정입니다.** 실제 의뢰서 파일로 확인해 라벨을 맞춰야 합니다. 맞추는 법: `node src/fixed.js dump 파일` 로 펼친 표를 보고, 라벨을 `labels` 에 추가한 뒤 `node src/fixed.js run 파일` 로 결과를 확인합니다. 양식이 여러 종류면 `rules/` 에 JSON 을 더 두면 가장 잘 맞는 규칙이 자동으로 선택됩니다.
- 원본 문서는 브라우저에서 못 여는 형식이라, 검토 화면의 원본 칸에 문서에서 읽은 글자(표는 `|` 로 구분)를 보여 줍니다.

### A 방식 동작과 한계
- 빈 양식 엑셀(`접수양식_빈칸.xlsx`: 접수, 시험항목, 작성예시, 안내)과 요청문(`src/prompts/claude-app.md`)은 도우미가 만들어 줍니다. 요청문에는 시료 1건 = 접수 1건, 체크박스 규칙, 노란 칸 표시와 "열 제목: 사유" 기재 방법이 들어 있습니다.
- Claude 앱이 노란 칸을 칠하지 못했더라도 "확인필요 항목" 칸에 적힌 사유는 불러올 때 확인 필요로 살립니다. (이 도우미가 저장한 엑셀은 기존처럼 노란 칸을 지우면 확인된 것으로 봅니다.)
- 정확도는 Claude 앱의 판독에 달려 있습니다. 사진 판독 결과는 반드시 검토 단계에서 원본과 대조하세요.
- **주의: A 방식도 의뢰서 사진(업체명, 연락처, 사업자번호 포함)이 Claude 서비스로 전송됩니다.** 사용 전에 기관 정보보안 정책을 확인하세요. B 방식은 외부로 전송하지 않습니다.

### 검증한 것 / 하지 못한 것
- 검증: 합성한 의뢰서(docx, hwpx, PDF)로 구역 구분·체크박스·시료 2건 분리·빈 칸 처리·양식 불일치 거절, 양식 엑셀 왕복, 서버 경로, 브라우저 화면 흐름(`npm test`).
- 미검증: 실제 의뢰서 파일에서의 인식률, 실제 Claude 앱에서 요청문과 양식으로 엑셀을 받는 과정(요청문 문구는 첫 사용 뒤 다듬어야 할 수 있음).
- 새 파일: `src/fixed.js`, `rules/`, `src/prompts/claude-app.md`, `test/`. 새 의존성: `jszip`, `pdfjs-dist`(PDF 글자 읽기).

## 13. 공유 서버 배포 (0.3.0, 2026-10-10)

여러 담당자가 서버 한 대의 주소로 접속해서 쓰는 방식을 추가했습니다. 내 PC 전용 모드(`시작.bat`)는 그대로입니다.

- **바뀐 구조**: 사번 연결을 서버 전역 하나로 들고 있던 것을 사용자별 세션으로 바꿨습니다(여러 명이 써도 서로의 사번 연결이 섞이지 않음).
- **접속 제한**: 접속 비밀번호(필수, 5번 틀리면 IP 10분 차단), 허용 IP/대역, 허용 사번, 허용 주소(Host)·Origin 검사, 쿠키 HttpOnly·SameSite=Strict(HTTPS 시 Secure·HSTS), 직접 HTTPS 또는 프록시 뒤 운영.
- **기록**: `logs/audit-월.log` 에 사번·시각·IP·동작만 남깁니다(의뢰서 내용·업체명·파일 이름·비밀번호는 남기지 않음).
- **배포 도구**: `deploy/install.sh`(Linux), `deploy/install.ps1`(Windows), `deploy/check.js`(점검), `.env.server.example`, `deploy/nginx.conf.example`.
- **문서**: 관리자용 `docs/서버배포.md`, 담당자용 한 장 안내서 `/guide.html`(A4 인쇄, 주소 자동 표시)와 `docs/담당자_사용안내서.pdf`.
- **검증**: `npm test` 27개(공유 서버 모드: 비밀번호·세션 분리·사번/IP 제한·잠금·기록 내용 포함), 내장 HTTPS(자체 서명 인증서)·쿠키 보안 속성, 설치 스크립트의 `--no-service` 경로와 서비스 파일 생성, 화면의 접속 비밀번호·사번 거부 흐름, 안내서 A4 1장 출력.
- **미검증**: Windows 설치 스크립트, systemd 등록 단계, nginx 예시, 실제 사내 서버에서의 연구관리시스템 연결.
- **주의(중요)**: 연구관리시스템의 사번 로그인에는 비밀번호가 없어서, 접속 비밀번호를 아는 사람이 다른 사번으로 연결할 수 있습니다. `ALLOWED_IPS`·`ALLOWED_EMPLOYEES` 설정과 접속 기록으로 통제하고, 연구관리시스템 쪽에서는 여러 담당자가 서버 한 대의 IP로 보이므로 도입 전 담당자와 협의하세요.
